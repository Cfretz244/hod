# WP-218: alignment directives in x86-64 templates

Spec: `spec/asm.md` §18 (and §8, §10.4, §13, §17);
`spec/codegen.md` §5.6.15 ("Alignment points").

## What was built

- `crates/hod_asm/src/x64/mod.rs`: `assemble_aligned(body, placement,
  longest, ..)` reads `.p2align`, `.balign` and `.align` (bytes on
  x86-64) with §17's operands. With `Placement::At(start)` it pads to
  boundaries counted from `start`; with `Placement::Reserve` it writes
  each directive's largest padding and returns the points as
  `AlignRow`s. A template branch across a directive that may pad is
  refused as `asm:align-crossed`. `assemble` still refuses the
  directives.
- `crates/hod_asm/src/align.rs`: `Align::most`, `fill_x64` (`nop`s of
  at most the given length, or the fill byte).
- `crates/hod_x64/src/tuning.rs`: the longest padding `nop` for each
  tuning CPU and tuning feature, measured from `llc`. An unmeasured CPU
  is `x64:align-tune-cpu`. `X64::nop` holds the function's value, and
  `X64::of_attrs_with` takes `-mcpu`/`-mattr`, passed by
  `crates/hod/src/back.rs`.
- `crates/hod_x64/src/barrier/template.rs`: a template that aligns is
  assembled reserved, and each point is handed to `FnCx::align_code`.
- `crates/hod_cg/src/shrink.rs`: alignment points are a third kind of
  edit. The padding kept is computed from the offset after the edits
  before it. Branch relaxation is a fixed point that bans a branch the
  padding puts out of reach, and every branch stays long when 32 passes
  do not converge. The kept bytes are filled again after compaction.
  Nothing changes for a function without points.

## LLVM's behaviour, measured with llvm-mc and llc 19 and 22

The `nop` rule is the one in `spec/asm.md` §18, measured for all 131
CPUs as `tune-cpu`, as `target-cpu` alone, with `tune-cpu` `i586` and
empty, with `-mcpu`, and with each tuning feature turned on and off.

- `llvm-mc`'s default CPU tunes as `generic` (15). Its `-mcpu=x86-64`
  gives 10, while `llc`'s `target-cpu` `x86-64` gives 15.
- `llc` caches subtargets under the joined CPU, tune and feature
  strings, so `"target-cpu"="skylake" "tune-cpu"=""` is given the
  subtarget of an earlier `"tune-cpu"="skylake"` function in the same
  module. The test keeps the two in separate modules.
- Fill `0x90` written positive: 19 writes `nop`s, 22 writes the byte.
- Fill 0 is zeros and fill -112 is `0x90` in both majors.

## Placement in one `.text`

hod counts from the function's start and aligns the function. `llc`
counts from the section offset and pads inside the function. hod's
placement was kept:

- Functions are compiled at offset 0 in parallel.
- The aligned instruction's address modulo the alignment, and the
  section alignment, are the same either way.
- With `-function-sections` the bytes are `llc`'s. In one `.text` they
  are `llvm-mc`'s at the template's section offset in both objects.

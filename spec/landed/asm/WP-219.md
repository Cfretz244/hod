# WP-219: constraints with alternatives (x86-64 and AArch64)

Spec: `spec/asm.md` §19.

## What was built

- `crates/hod_cg/src/asm_constraints.rs` has the following:
  - `TieShape` and `Ties`, which hold LLVM's ties:
    - the top-level `MatchingInput` set by an input without
      alternatives;
    - each alternative's tie, set by an input with alternatives;
    - `selectAlternative`'s rule, which drops the top-level tie of an
      output with alternatives.
  - `Ties::matching`, the tie in effect under the chosen alternative.
  - `Ties::pairs`, every tie some alternative can put in effect.
  - `AltError::Parse` (`llc`'s "failed to parse constraints") and
    `AltError::Count` (an operand with fewer alternatives than another,
    but more than one).
- x86-64 (`hod_x64::barrier`, `barrier::template`):
  - Whether an output is tied comes from `Ties`, so an untied output with
    a memory code takes its memory.
  - `x` weighs 1 for 128 bits, or for 256 bits with AVX. `v` also weighs
    1 for 512 bits with AVX-512 (LLVM's `getPrimitiveSizeInBits`).
  - A tied input placed in its output's memory is not read.
  - New refusal: `x64:inline-asm-alternative`.
- AArch64 (`hod_a64::barrier`, `inline_asm`): the same rules, and the
  refusal `a64:inline-asm-alternative`. A tied input in memory no longer
  overwrites the output's pointer register with its slot address.

## How the rule was measured

Every shape was run through `llc` 19 and 22 at `-O0`, with AArch64 also
at `-global-isel=0 -fast-isel=0`. The grid covered `=*imr|x,0`,
`=*imr|x,0|0`, `=*x|r,0`, `=*r|x,0`, direct `=r|x,0` and `=x|r,0`, and the
inputs `imr|x`, `r|x`, `x|r`, `rm|x`, `x|m` and `m|x`. It used the types
i8 to i128, `float`, `double`, `x86_fp80`, `ptr`, and vectors of 128, 256
and 512 bits, with and without AVX and AVX-512. The AArch64 grid did the
same with `w`. The two majors agree on every case.

The source of the rule is LLVM's `TargetLowering::ParseConstraints`
(the weights) and `InlineAsm::ConstraintInfo::selectAlternative` (the
ties). The tests compare the operand class of the template's instruction
in hod's objects and `llc`'s:

- `crates/hod_x64/tests/asm_alternatives.rs` `alternatives_are_llcs_choice`:
  68 cases;
- `crates/hod_a64/tests/asm_alternatives.rs`: 31 cases.

## Evidence

- Kiln-built programs `barrier.cpp`, as `barrier.ll` and
  `barrier-g.ll`, were compiled by kiln 1.1.0, binary dated 2026-11-14
  10:48, at kiln 21b9110a4.
  - x86-64 types: `"+g,x"` on `int`, `long`, `short`, `char`, `float`,
    `double`, `__int128`, a pointer, `__m128`, `__m128d`, `__m128i` and
    `__m256` (an AVX function).
  - AArch64 types: `"+g,w"` on the scalars, `float32x4_t`, `float64x2_t`
    and `int32x2_t`.
  - Both programs also include templates with alternatives.
- These programs and the `semantics.ll` drivers were built by hod and by
  `llc` 19 and 22, then linked and run with every combination of:
  - hod builds: plain, stress, far, and the x86-64 large code model;
  - linkers: bfd, lld and mold;
  - linking: dynamic and static;
  - runs: x86-64 under qemu with `-cpu max`, AArch64 natively.
  - 108 x86-64 programs and 90 AArch64 programs ran, every check passing.
- The 8 Eigen x86-64 TUs that strict mode declined were compiled through
  kiln with `KILN_HOD_STRICT=1`: packetmath_1, _2 and _14, array_cwise_2,
  _3 and _5, and special_functions_1 and _2. Kiln's stats log gives
  `backend` `hod` for all 8.
- Byte identity was checked base (3b14f8ff) against head over every 10th
  text entry of `.build/corpus` and `.build/corpus-x64`. Each was built in
  its own target directory, and `scripts/corpus-bytes.py` compared them.
  - AArch64: 625 entries, 674 modules, 674 objects identical.
  - x86-64: 627 entries, 676 modules, 676 objects identical.
  - Nothing differs.
- `dcl.asm` (Benchmark's `DoNotOptimize`, `=*r|m,0`, `=*m|r,0`, `r|m`) is
  byte-identical, base against head, on both targets and both LLVM
  versions. Neither stores the input, and neither does `llc` 19 or 22.

# WP-178 — LLVM built by kiln and hod

Landed: LLVM 19.1.7 (tag `llvmorg-19.1.7`, the tag of kiln's
`llvm_clang` row) configured for `-O0` with assertions and the AArch64
and X86 back ends, built by kiln with hod as its back end, with every
tool and unit test of `check-llvm`, and `check-llvm` run against a
control built from the same tree with the same flags by kiln with its
LLVM back end. **check-llvm is at parity**: 36338 lit tests and 8007
unit tests (68 binaries) give the same per-test results in both trees.
Of 2779 translation units, hod wrote the object of 2777; one module hod
declines (`attr:disable-tail-calls`, googletest), and one TU kiln never
offers to hod (a false positive of kiln's `instrument-entry` trigger).
Every tool of `check-llvm` and every unit-test binary was built again in
strict mode, with no fallback, and passed; the two TUs above were built
outside it. Clang built the same way (hod refuses nothing in it) and 12
directories of its lit tests (12460 tests) are at parity: see "Clang".

The scripts are `scripts/oss/llvm/` (the record of every command); the
census the supervisor read while the work ran is
`.build/findings/oss/LLVM-CENSUS.md` of the workspace, with the saved
modules under `.build/findings/oss/llvm/<refusal>/`.

## Setup

- Host: aarch64 Linux, shared and loaded (load average 30 to 35 on 24
  cores during the builds and tests). Target: `aarch64-unknown-linux-gnu`.
- kiln 1.1.0 (`kiln++` for C++, `kiln` for C) in both trees; hod: a
  release build of `hod_cli` at `95cf7e9` (this branch's base), frozen
  into the hod tree's `bin/hod`.
- Source: a shallow clone of the tag (`scripts/oss/llvm/clone.sh`).
- Two trees from the one source, configured by `configure.sh hod|llc`
  with kiln's row's flags without its projects, at `-O0` and without
  `-g`: `-G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_FLAGS_RELEASE=-O0
  -DCMAKE_C_FLAGS_RELEASE=-O0 -DCMAKE_CXX_STANDARD=17
  -DLLVM_TARGETS_TO_BUILD="AArch64;X86" -DLLVM_ENABLE_ASSERTIONS=ON
  -DLLVM_INCLUDE_TESTS=ON -DLLVM_INCLUDE_BENCHMARKS=OFF
  -DLLVM_INCLUDE_EXAMPLES=OFF -DLLVM_ENABLE_ZSTD=OFF
  -DLLVM_ENABLE_LIBXML2=OFF -DLLVM_USE_LINKER=mold
  -DLLVM_PARALLEL_LINK_JOBS=1 -DLLVM_LIT_ARGS="-sv -j 4"`. Static
  libraries and tools (no shared libLLVM). No per-target `-O` flag
  appears in `build.ninja`: every TU compiles at `-O0`.
- The compilers are `wrap.sh` under four names (`kiln-hod-cxx`,
  `kiln-hod-cc`, `kiln-llc-cxx`, `kiln-llc-cc`), which run kiln's own
  logging wrapper (`kiln/scripts/oss/kiln-cxx`, `kiln-cc`: a 3 GB
  address-space cap and a timeout per compile, one JSON line per
  invocation in `logs/tu.jsonl`) with: `KILN_BACKEND=hod`,
  `KILN_HOD=<tree>/bin/hod`, `HOD_COVERAGE_LOG=<tree>/logs/coverage.tsv`
  and `HOD_CENSUS=1` (hod tree), `KILN_BACKEND=llvm` (control), and
  kiln's statistics log `KILN_STATS_LOG=<tree>/logs/stats.jsonl` (both).
  A link gets 16 GB of address space instead of 3: mold maps every `-O0`
  archive whole, and the first links of `llc` and `opt` failed under
  the compile cap (`mmap failed: Cannot allocate memory`).
- Builds: `build.sh <tree> <stage> <targets>` (`ninja -j 6` at most, `-j
  3` or `-j 4` when both trees built at once, `-k 0`).
- **Strict mode** (`HOD_OSS_STRICT=1`, `strict.sh`): kiln's
  `KILN_HOD_STRICT=1` makes only a hod *failure* an error; a decline
  (hod's status 2) still falls back to `llc` silently, and a job kiln
  does not offer to hod never reaches it. So in strict mode the wrapper
  gives each compile its own statistics log and fails the compile
  (removing its object) unless every object job of it says backend
  `hod` (`strict-check.py`).
- The census (`census.py`, `census-file.sh`) joins `tu.jsonl`,
  `coverage.tsv` (by the object path: field 5 is kiln's `-o`, relative
  to the wrapper's working directory) and `stats.jsonl` (by input), and
  saves up to three modules per refusal name (`save-modules.py`: the
  TU's command again with `-S -emit-llvm`, the module kiln hands its back
  end at `-O0`; hod's own answer on it and the command line beside it).

## Census: every refusal

| name | modules | example function | module |
|---|---:|---|---|
| `attr:disable-tail-calls` | 1 | `testing::internal::UnitTestImpl::CurrentOsStackTraceExceptTop` and `testing::internal::GetCurrentOsStackTraceExceptTop` of googletest's `gtest-all.cc` (`GTEST_NO_TAIL_CALL_`, `__attribute__((disable_tail_calls))`, gtest-port.h:859) | `findings/oss/llvm/attr:disable-tail-calls/gtest-all.cc.ll` |

`HOD_CENSUS=1` names no other reason in that module or in any other.
hod's message names the construct but not the function (a module-level
attribute group): the functions were found through the group. Every
gtest unit test links this object, so it is the one module between
`check-llvm`'s unit tests and a build with no fallback at all. The
attribute is a string attribute missing from hod's table
(`crates/hod_ir/src/attrs.rs`, the `st(...)` rows), so the reader
refuses it as unknown; whether it can be dropped (hod's tail calls) is
for the package that takes it, not fixed here.

**Not offered to hod (a kiln finding).**
`lib/Transforms/Utils/EntryExitInstrumenter.cpp`: kiln's opt trigger
`instrument-entry` is a text search,
`ir.contains("\"instrument-function-entry")`
(`kiln/crates/kiln_driver/src/codegen_cmd.rs:1145`), and the TU's own
string constant `c"instrument-function-entry\00"` (the attribute name
the pass reads) matches it. kiln routes the TU to `opt` + `llc`; with
the trigger fixed it would be an ordinary module.

## Clang

The same two trees reconfigured with `HOD_OSS_PROJECTS=clang`
(`LLVM_ENABLE_PROJECTS=clang`; LLVM not rebuilt), target `clang`.

- **Build**: the hod tree strict first (`c1-strict`, `-k 0`): one
  failure, kiln's again: `clang/lib/CodeGen/CodeGenFunction.cpp` holds
  the string `"instrument-function-entry"` (the attribute clang writes),
  so kiln's `instrument-entry` trigger keeps it from hod, as with
  `EntryExitInstrumenter.cpp`. That TU was built outside strict (`c1b`),
  then `clang` linked strict (`c1-strict2`, rc 0). **hod refuses nothing
  in clang**: of 3623 TUs over LLVM and clang, hod wrote 3620 (the
  googletest module above and the two not offered are the rest). The
  hod-built `clang` (500 MB, static, `-O0`) compiles, links and runs a
  C++ program.
- **Tests**: `clang-test-depends` (about 20 more static `-O0` tools of
  300 to 500 MB each) did not fit in both trees, so the lit slices that
  need only `clang` and the LLVM tools already built were run
  (`clang-lit-slices.txt`: CodeGen, CodeGenCXX, SemaCXX, Sema, CXX,
  Driver, Preprocessor, Parser, Lexer, SemaTemplate, AST, C): **12460
  tests, 9972 pass, 13 xfail, 2463 unsupported, 12 fail, the same per
  test in both trees.** The 12 failures are in the control too:
  case-insensitive include tests (4, the file system is case-sensitive),
  Driver tests of tools not built (5), `Sema/warn-documentation*.cpp`
  (2) and `Parser/skip-function-bodies.mm` (1). The rest of check-clang
  (the other directories, the clang unit tests) was not run.

## `-g` census (compile only)

`scripts/oss/llvm/g-census.py` re-runs a sample of a built tree's TUs
with `-g` through kiln with strict mode off, deleting each object as it
is produced. kiln 21caaf874, hod d845ec5:

- native, every 11th TU: 330 TUs, compile rc 0 for 330; object jobs
  **hod 328, hod-declined 2**, both `debug:invalid`
  (`llvm/lib/CodeGen/MachineDominators.cpp`, `MachineRegionInfo.cpp`).
- x86-64, every 9th TU: 311 TUs, rc 0 for 311; **hod 310,
  hod-declined 1**, `debug:invalid` (`MachineRegionInfo.cpp`).
- `debug:invalid` is invalid IR from kiln: one function gets two distinct
  `DISubprogram`s. The function's `!dbg` names one; its locations and its
  `this` variable name the other. LLVM's verifier reports "!dbg
  attachment points at wrong subprogram for function" and "conflicting
  debug info for argument". `llc` then drops the module's debug info
  ("ignoring invalid debug info"), so the fallback object has none.
  hod's refusal is correct. A reduced module (one function, two
  subprograms) gets the same verdict from both.

## Side note: time

Not a benchmark: the host was shared and loaded, the two trees were
often built at the same time, and the hod tree's compiles ran during
its strict rebuilds and the lit runs (`compare-time.py`). Over the 2779
TUs of both trees, summed per TU (front end and back end, kiln's
wrapper's child times): hod tree wall 7399 s, CPU 4501 s; control wall
6483 s, CPU 4611 s. kiln's own split (statistics log, `children_ms`):
the back end took **225 s in hod** against **794 s in the control**
(`llc` 625 s, `opt` 169 s: the `alwaysinline` modules go through `opt`
in the control and not with hod); the front end dominates both. Peak
compile RSS: 583 MiB (hod tree), 790 MiB (control). Stage wall times
(ninja, both trees building at once at `-j 3`): s1 187 s / 197 s, s2
1175 s / 1227 s.
